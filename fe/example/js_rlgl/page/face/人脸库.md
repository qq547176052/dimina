# 人脸库管理（小程序端 + Go 后端）对接设计文档

> 范围：人脸库「筛选列表 / 添加 / 编辑 / 删除 / 同步」五个能力的小程序（dimina）前端
> 与 `code_sh/dd` 后端的对接设计。本文为**设计文档**，先对齐方案，再落地代码。
>
> 履历：
> 2026-07-27  v1.0  初版设计：梳理现有本地人脸库文件结构、已有接口与摄像头协议，
>             设计 5 个能力的后端接口契约与小程序页面/数据流。
> 2026-07-27  v1.1  纠正增删改与「同步」的协作关系：同步第 2 步(所有摄像头→本地)
>             会覆盖本地，故「添加/编辑」改为「推主摄像头 + 触发同步(fan-out)」，
>             「删除」改为「先删所有摄像头(避免同步复活) 后删本地」。
> 2026-07-27  v1.2  落地实现并明确「编辑专用同步」与旧全量同步解耦：新增
>             `F同步编辑后(被编辑IP)`（被编辑摄像头→本地 / 钉钉→本地 / 合并工号 /
>             本地→所有摄像头除被编辑）；camApi 新增 F删除人员/F查摄像头内PIDBy姓名/
>             F从所有摄像头删除人员/F推单人到摄像头/F导出单摄像头到本地，重构抽出
>             F导入人脸库到所有摄像头除；后端 POST/PUT/DELETE /dd/face-library 及
>             补注册 GET /dd/face-library 均已落地（`3_编辑一台摄像头人脸库然后同步.go` / `main.go`）。

## 3. 总体架构与数据流

```
┌──────────────┐    HTTPS /dd/face-library/*    ┌─────────────────────┐
│ 小程序(dimina) │ ───────────────────────────▶ │  Go 后端 (code_sh/dd) │
│ page/face/*   │ ◀─────────────────────────── │                     │
└──────────────┘    JSON / multipart            └──────────┬──────────┘
                                                          │ camApi
                                                          ▼
                                                ┌─────────────────────┐
                                                │ 摄像头人脸库 (/person/*) │
                                                └─────────────────────┘
       后端本地持久化（文件）：
       数据/导出人脸库/人脸照/{姓名}.jpg  +  人脸名单.xlsx
```

- **读路径**：列表/图片只读本地文件（xlsx + jpg），不依赖摄像头实时状态。
- **写路径**：增/改/删 既改本地文件，又通过 camApi 同步到所有摄像头。
- **同步**：`/sync` 为全量对齐（钉钉工号 + 摄像头照片 ↔ 本地），与单条增删改互补。

## 5. 后端接口设计（新增/补充）

统一响应包装：`{ "code": 200, "success": true, "message": "...", "data": {} }`；
失败：`{ "code": 400, "success": false, "message": "错误描述", "data": null }`。

### 5.1 `GET /dd/face-library`（筛选列表 —— 已有，明确契约）

请求 Query（均可选）：`page`(默认1) `pageSize`(默认20) `faceLibrary`(whitelist/blacklist/vip/visitor) `name` `employeeNo` `phone` `idCard` `department`。
响应 `data`：`{ list: T人脸列表项[], total, page, pageSize }`。

> 前端注意：`imageName` 可能对应不存在的 jpg（同步异常时），展示需兜底默认图。
> 建议（可选增强）：后端补充返 `faceImageUrl` 完整 URL，前端免拼接；**本期保持现状**（返 imageName，前端拼）。

### 5.2 `POST /dd/face-library`（添加人脸 —— 新增）

**请求**：`multipart/form-data`（小程序用 `wx.uploadFile` 发送单文件 + 表单字段，避免大图 base64）

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `photo` | file | 是 | 人脸照片（jpg/png） |
| `name` | string | 是 | 姓名（主键；重名则覆盖更新已有） |
| `faceLibrary` | string | 是 | whitelist/blacklist/vip/visitor |
| `employeeNo` | string | 否 | 工号 |
| `department` | string | 否 | 部门 |
| `gender` | string | 否 | 男/女 |
| `age` | string | 否 | |
| `idCard` | string | 否 | |
| `phone` | string | 否 | |
| `icCardNo` | string | 否 | |
| `validityType`/`validityStartTime`/`validityEndTime`/`other` | string | 否 | |

**后端处理步骤**：
1. 校验 `name`、`faceLibrary` 合法；`faceLibrary` 非法 → 400。
2. 照片存盘：`人脸照/{name}.jpg`（覆盖）。
3. xlsx upsert：按 `name` 找行，无则新增（编号取当前最大+1），写入各字段；`图片名称`={name}.jpg；`黑白名单`=API→中文。
4. **推主摄像头**：调用 `F推单人到摄像头(主摄像头, name)`（按姓名 add 到「第一台配置摄像头」即可；无需逐台推，fan-out 交给专用同步）。
   > 为什么只推一台：编辑专用同步 `F同步编辑后` 第 1 步「被编辑摄像头→本地」会把此人从主摄像头拉回本地（并补钉钉工号），第 4 步「本地→所有摄像头（主摄像头除外）」fan-out 到其余摄像头。所以 **add 只推主摄像头**即可。
5. **触发专用同步**：`go F同步编辑后(主摄像头IP)` —— 见 5.7（**不复用**旧 `F同步钉钉摄像头本地人员信息`；旧同步第 2 步拉「全部」摄像头覆盖本地，语义不同）。
6. 返回新人信息：`{ name, faceLibrary, imageName }`。

> 容错：主摄像头推送失败 → 降级 `F导入人脸库到所有摄像头()` 直接推全部（不走专用同步，等价于旧行为）；故主摄像头需可用，否则退化为整库推送。

### 5.3 `PUT /dd/face-library`（编辑人脸 —— 新增）

**请求**：`multipart/form-data`（换照片时带 `photo`，否则不带）

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `name` | string | 是 | 原姓名（定位要改的人） |
| `newName` | string | 否 | 改名时用；改名需同步改 jpg 文件名 + xlsx 图片名称 + 摄像头 name |
| `photo` | file | 否 | 新照片，覆盖 `人脸照/{name}.jpg` |
| 其余字段 | string | 否 | 同 5.2，缺省不覆盖 |

**后端处理步骤**：
1. 按 `name` 在 xlsx 找行，无则 404。
2. 改 xlsx 字段；缺省字段（工号/部门/电话/身份证/类别）沿用现有值，**不误清空**。
3. 若 `photo` 存在 → 覆盖 `人脸照/{最终姓名}.jpg`。
4. 若 `newName` 存在 → 先删旧 xlsx 行 + 重命名 jpg，再 upsert 新行。
5. 推摄像头（作用在**主摄像头**，改完触发专用同步）：
   - **仅字段变**（工号/类别，不换照）→ `F查摄像头内PIDBy姓名` 找 pid → `F更新人员信息(pid)`。
   - **换照** → `F删除人员(pid)`（按原姓名定位）+ `F推单人到摄像头(主摄像头, 最终姓名)`（重新 add，因 `F更新人员信息` 协议不传 photo，纯 update 改不了脸）。
   - **改名** → 主摄像头先 delete 旧 `name`，再 add 新 `name`（摄像头以 name 判重，改名必须 delete+add）。
6. **触发专用同步**：`go F同步编辑后(主摄像头IP)`（见 5.7）。
7. 返回更新后信息：`{ name, faceLibrary, imageName }`。

### 5.4 `DELETE /dd/face-library`（删除人脸 —— 新增）

**请求**：`DELETE /dd/face-library?name={姓名}`（URL encode）。
**后端处理步骤**（⚠️ 顺序关键：先删摄像头，后删本地）：
1. **摄像头**：调用 **`F从所有摄像头删除人员(name)`**（已实现：遍历每台摄像头 `F获取Token`→`F查摄像头内PIDBy姓名` 按姓名找 pid→`F删除人员(pid)`；无此人的摄像头计成功）。
   - 返回 `(成功, 失败)`；任一摄像头失败需**重试至成功**；只要有一台残留此人，下次同步就会把它从摄像头拉回本地「复活」。
   - 删除**不触发**同步（否则残留摄像头反而会借同步重新铺开）。
2. **本地**：删 xlsx 行 + 删 `人脸照/{name}.jpg`（不存在忽略）；必须在摄像头清空之后，避免窗口期内同步复活。
3. 返回 `{ name, cameraOK, cameraFail }`。

### 5.5 照片上传方式决策

- **小程序侧**：`wx.chooseImage` 选图 → `wx.uploadFile({ url, filePath, name:'photo', formData:{...字段} })`。
- **理由**：先前 `5_抓拍分发.go` 已因「全身照 base64 过大」改为传 URL，故添加人脸同样**避免 base64**，用 multipart 直传文件。
- 后端统一用 `c.FormFile("photo")` + `c.PostForm(...)` 解析（非 JSON body）。

### 5.6 摄像头侧实现（camApi，已落地 `人脸库编辑同步.go` + 重构 `导入人脸库.go`）

1. `F删除人员(ip, token, pid string) error` —— 调 `/person/delete`（协议 1.12）。
2. `F查摄像头内PIDBy姓名(ip, token, name string) (pid string, ok bool)` —— 按姓名在单台摄像头查 pid（删除/更新前置）。
3. `F从所有摄像头删除人员(姓名 string) (成功, 失败 int)` —— 遍历所有摄像头按姓名找 pid 后 `F删除人员`；无此人的摄像头计成功。
4. `F推单人到摄像头(摄像头 B摄像头列表, 姓名 string) error` —— 把本地一人增量推到单台摄像头（add 或 update，复用 `推一人到摄像头增量`）。
5. `F导出单摄像头到本地(被编辑IP string)` —— 把**单台**摄像头人脸库覆盖导出到本地（编辑同步第 1 步，区别于拉全部的 `F导出人脸库到本地`）。
6. `F导入人脸库到所有摄像头除(排除IP string)` —— 本地→所有摄像头但跳过被编辑那台（编辑同步第 4 步；由 `F推本地人脸库到单摄像头` 重构复用）。
7. （可选）扩展 `F更新人员信息` 支持 `photo` 参数 —— 满足「纯换照、不删除重建」的编辑场景（当前协议实现不传 photo，故换照走 delete+add）。

### 5.7 编辑专用同步 `F同步编辑后(被编辑IP)`（新增，不复用旧同步）

> 旧 `F同步钉钉摄像头本地人员信息`（即 `/sync`）第 2 步是「**所有**摄像头→本地」拉全量覆盖本地；
> 编辑只动「第一台摄像头」，语义不同，故新建专用链路，顺序：

1. **被编辑摄像头 → 本地**：`F导出单摄像头到本地(被编辑IP)` —— 单台覆盖导出（以被编辑摄像头为准）。
2. **钉钉 → 本地**：`F获取钉钉人员到本地()` —— 写 `B钉钉人员` 表。
3. **合并钉钉工号到本地**：`合并钉钉工号到本地人脸名单()` —— 按姓名回写工号列。
4. **本地 → 所有摄像头（被编辑摄像头除外）**：`F导入人脸库到所有摄像头除(被编辑IP)` —— fan-out 到其余摄像头。

对应后端调用方：`F添加人脸` / `F编辑人脸` 推完主摄像头后 `go F同步编辑后(主摄像头IP)`。

> ⚠️ 分歧风险：第 1 步用「被编辑摄像头」覆盖本地——若各摄像头数据已不一致（某些人仅存在于其它摄像头），这些人会从本地与第 4 步被清除。常规部署各摄像头一致时无影响；若需保留分歧人员，应改为「合并」而非「覆盖」（后续增强）。

### 6.4 API 封装（基于现有 `config.js`）

复用 `config.js` 的 `host` 与登录态（`本地数据.token`）。新增 `faceApi.js`：

```js
const config = require('../../config.js')
function _token() { return config.读取本地数据().token || '' }
function _img(name) { return `${config.host}/dd/face-library/image/${encodeURIComponent(name)}` }

// 列表（JSON）
function listFace(params) {
  return new Promise((res, rej) => wx.request({
    url: `${config.host}/dd/face-library`,
    method: 'GET', data: params, header: { Authorization: 'Bearer ' + _token() },
    success: r => r.data.success ? res(r.data.data) : rej(new Error(r.data.message)),
    fail: () => rej(new Error('网络错误')),
  }))
}
// 添加（multipart，wx.uploadFile）
function addFace(formData, filePath) {
  return new Promise((res, rej) => wx.uploadFile({
    url: `${config.host}/dd/face-library`,
    filePath, name: 'photo', formData,
    success: r => { const d = JSON.parse(r.data); d.success ? res(d.data) : rej(new Error(d.message)) },
    fail: () => rej(new Error('网络错误')),
  }))
}
// 编辑 / 删除 类似（PUT multipart / DELETE query）
```

> 鉴权头 `Authorization: Bearer {token}` 与现有 `/dd` 组一致（`admin_02` 守卫）。

## 7. 关键流程（后端处理步骤小结）

- **添加**：校验 → 存 jpg → upsert xlsx → `F推单人到摄像头(主摄像头)` → `go F同步编辑后(主摄像头IP)` 专用同步 fan-out → 返新行。
- **编辑**：定位行 → 改 xlsx（字段沿用现有值）→（换照/改名→主摄像头 delete+add；改字段→主摄像头 update）→ `go F同步编辑后(主摄像头IP)` → 返更新行。
- **删除**：`F从所有摄像头删除人员(name)`（先，重试保证全清）→ 删 xlsx 行 + 删 jpg（后）→ 返成功（**不触发同步**）。
- **同步（编辑专用）**：`F同步编辑后` = 被编辑摄像头→本地、钉钉→本地、**合并工号**、本地→所有摄像头(除被编辑)。
- **同步（全量 `/sync`）**：`F同步钉钉摄像头本地人员信息` 仍保留给「手动全量同步」按钮（钉钉→本地、所有摄像头→本地、合并工号、推摄像头）。

> 路由均已注册于 `main.go`：`GET/POST/PUT/DELETE /dd/face-library`（其中 `GET` 列表接口此前未接线，本次补注册）。

## 8. 风险与注意

1. **姓名即主键**：重名将相互覆盖（与现有同步逻辑一致）；若未来出现重名，需引入 `work_id` 优先 + 重名跳过策略（见 `导入人脸库.go` 假设）。
2. **xlsx 并发写**：多次增删改可能并发写同一 xlsx；建议后端加单飞/文件锁，或同步操作串行化（与 `/sync` 互斥）。
3. **摄像头换照限制**：`F更新人员信息` 当前不传 photo，编辑换照走 delete+add（已由 `F删除人员`+`F推单人到摄像头` 实现，见 5.3/5.6）。
4. **大图上传**：小程序用 `wx.uploadFile` 直传，避免 base64 撑爆请求（呼应 `5_抓拍分发.go` 决策）。
5. **本地落库优先于摄像头**：摄像头推送失败仅 log，不阻断本地；前端以本地列表为准。
6. **图片缺失兜底**：`imageName` 可能无对应 jpg，前端必须兜底默认图。
